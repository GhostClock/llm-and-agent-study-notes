# 第 2 章　RAG 检索链路

## 2.1　为什么要分块

### 2.1.1　索引粒度决定检索上限

#### 2.1.1.1　向量是定长压缩
（1）压缩会丢掉局部信息
把五十页文档压成一个向量，局部信息会被平均掉，向量只能说明这份文档大概在讲什么。
你没法从这个向量里问出「第十二页那个参数是多少」，它已经在压缩中和别的语义混在一起了。

（2）召回单元要接近回答单元
检索返回的是块，喂给模型的也是块。块比答案大，噪声就稀释注意力；块比答案小，答案就被切成两半。

#### 2.1.1.2　上下文是有限预算
把整库塞进 prompt 并不可行。长上下文模型也有 lost-in-the-middle：中间位置的内容命中率明显低于首尾。
每问一次都送五万 token 和送两千 token，是二十五倍的延迟与费用差距。

### 2.1.2　长上下文能不能取代分块
语料只有几千字时，不分块、直接全文喂给模型更准也更省事，这也是长上下文的正当用法。
一旦语料超过单个模型的上下文预算，或者需要持续增删文档，索引与分块就从优化变成了必需。

## 2.2　常见分块方法
### 2.2.1　规则型方法
#### 2.2.1.1　定长切分
固定 token 数硬切，块长完全可控，实现最简单。代价是句子被拦腰截断，块首尾都是残句。

#### 2.2.1.2　递归切分
给一个分隔符优先级列表，超长片段逐级降级，尽量落在自然边界，多数语料的默认起点。

#### 2.2.1.3　结构切分
按文档自己的标题层级切，块边界与章节边界重合，每块自带面包屑元数据。

### 2.2.2　模型型方法
#### 2.2.2.1　语义切分
检测相邻句向量的距离跳变，在话题切换处断开。索引阶段要多跑一遍 embedding，阈值必须按本地语料定。

#### 2.2.2.2　命题化切分
让模型把段落拆成一条条可独立阅读的原子陈述。块最干净，也最贵最慢，结果还不稳定。

## 2.3　参数怎么定
### 2.3.1　从评测出发，而不是抄默认值
分块与 embedding 模型、top-k、rerank 是一套联调的组合，换其中任何一个都可能要让分块参数重调。
验收指标只能是真实 query 下的召回率与最终答案的幻觉率，猜不出来，必须测。
